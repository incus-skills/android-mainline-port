## 3. 故障主题

### 测量与优化

开头案例记录了一个超过 40 分钟的根文件系统构建：在没有测量的情况下盲目尝试提速。分段计时后，主要耗时来自 QEMU 全系统模拟中的 dracut 和清理通用内核，而不是发行版包安装。

规则是记录每一步耗时；首次遇到超过五分钟的步骤就进一步分段计时。

其他案例继续强调先测量：
- 更换 OUT 路径会因路径进入编译参数和缓存键而使 ccache 失效；
- ccache 容量不足、路径变化造成 manifest 膨胀和低命中率；
- 如果发行版基础层不是瓶颈，缓存它反而可能使构建更慢；
- Ubuntu 的 dracut 可能把不同 zstd 压缩等级映射为同一等级；
- 主机磁盘、内存、并行构建和 Wi-Fi 上传可能成为实际瓶颈。

这些时间和比例按源文记录，本轮没有独立基准测试。

### 执行环境与架构

源文件区分原生 ARM64、root 权限 qemu-user chroot 和 QEMU/TCG 全系统模拟。全系统模拟仅用于必须验证 init 行为的测试，并且不应并行运行多个全系统虚拟机。

无特权用户命名空间的问题不只是速度：UID/GID 属主映射和设备节点创建可能错误。源文件给出的替代方式是真正的 root（并把免密 sudo 限制到固定脚本）或原生 CI。

Mesa 是独立的极端案例：qemu-user 下 NIR Python 代码生成器耗时超过 100 分钟，而原生只需几十秒。建议交叉编译或原生 ARM64 编译。

### 缓存与构建输出身份

OUT/ccache 案例区分：
- 每种配置使用长期 OUT 路径；
- ccache `base_dir` 和 manifest 增长；
- 用 `flock` 保证同一 OUT 只有一个写入者；
- 记录构建输入身份；
- 构建前核对当前源码 HEAD，不匹配就拒绝；
- 已记录身份的 OUT 不再写入。

源文件还区分普通缓存与有身份记录的构建产物。带提交的 worktree 或被收据引用的 OUT 不能随意删除。

### 可复现性

源文件把相同源码构建出不同结果归因于多个独立输入：
- ccache 与直接 GCC 的调试信息源文件路径不同；
- `KAFLAGS` 缺少路径映射；
- umask 改变目录权限；
- APT 索引没有固定；
- 宿主机 `dtc` 版本不同；
- AVB salt 默认随机。

列出的控制措施包括同时在 `KCFLAGS` 和 `KAFLAGS` 中加入路径映射、固定内核构建时间戳/用户/主机、归一化权限与时间戳、使用确定性 tar 排序，以及固定 AVB salt。

这是源文件列出的控制措施；本轮不声称它们覆盖所有输入，也不声称应用后必然保证逐位可复现。

### 发布完整性与分发

发布条目涉及：
- GitHub Release 单附件 2 GB 限制和根文件系统分卷；
- 面向用户的发布说明与适量归类的附件；
- 首日确定提交作者；
- 已存在同上游 fork 时 `gh repo fork` 的副作用；
- GPL 源码随发布提供及非官方商标表述；
- 发布包版本高于测试设备已有内部版本；
- 已发布标签不可移动；
- 清理前核对发布清单与收据；
- 将身份记录移出待删除目录。

源文件还区分对外文档和内部调查记录。对外文档说明功能、支持范围、安装和校验方式，保留安全提醒，但不向用户倾倒内部根因分析或技术债编号。

### 增量工作与版本节奏

Mesa 案例记录构建入口默认删除旧目录，而 resume 选项拒绝已进入打包阶段的目录。处理方式是按源码和补丁哈希保留构建目录，并支持增量重编。

最后的版本推进条目描述每个版本的重复节奏：确定范围和验收方式、开发、测试、收尾发布、清理分支/worktree/旧产物，然后开始下一次移植。不要积累未发布候选，新功能等当前版本发布后再开始。

这是源文件描述的工作节奏，不是正式状态机。

## 5. 观察者重构出的对应关系

以下是观察者重构出的对应关系，不是源文件定义的统一模型：

- **优化前先测量：**性能判断来自分段测量，而不是猜测哪个层最慢。
- **执行环境是变量：**原生 ARM64、qemu-user 和 QEMU 全系统模拟不是可互换的构建/测试环境。
- **缓存身份与产物身份：**缓存可按输入复用或丢弃；已记录身份的 OUT 和被发布引用的文件则有保留约束。
- **路径也是构建输入：**路径会影响缓存键和调试元数据，因此目录布局同时影响速度与可复现性。
- **可复现性由多个输入共同约束：**源码提交本身不足以保证产物相同；工具链、索引、路径、时间戳、权限和随机 salt 也有影响。
- **产物来源与发布完整性：**源码 HEAD、构建输入身份、发布清单、收据、哈希和已发布标签承担不同职责。
- **内部证据与公共接口：**技术债和根因分析属于内部记录；发布文档服务于用户判断和安全操作。
- **版本边界作为工作控制：**按版本推进限制未发布候选积压，并把新功能推迟到当前版本发布之后。
