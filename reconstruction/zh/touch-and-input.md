## 1. 文档角色

该文档是输入子系统的领域经验记录，覆盖触控、按键、键盘配件和指纹。标题还列出手写笔，但正文没有独立的手写笔实现路线、验收标准或故障条目。这个缺口应被保留，不能从触控或键盘内容推断手写笔实现。

文档结构由推荐路线、完成标准、具体故障经验和未解决事项构成。它并未定义一个统一的输入设备架构；不同设备的硬件形态、固件位置、协议、电源生命周期和用户态入口各不相同。

## 2. 推荐路线的结构

### 触控：先区分硬件形态

源文件明确区分三种触控结构：

1. **独立触控芯片，固件在芯片 flash 中**：驱动相对独立，按普通 I2C/SPI 外设处理。
2. **TDDI，固件在 RAM 中**：面板复位会丢失触控固件，驱动必须跟随面板电源序列，并在面板每次上电后重新下载固件。
3. **THP，原始数据加主机算法**：内核负责固件下载和原始帧传输，用户态算法计算触点；依赖开源算法和本机标定数据。

随后给出证据优先的实现路线：读取厂商源码和原厂日志；只有没有源码时才反汇编；以同系列主线驱动为基础；参考同 SoC 设备的节点结构，但数值必须来自目标设备；逐函数对比帧格式；接入面板电源序列；最后标定方向。

### 按键

按键路线与本机 PMIC 和设备树描述绑定：
- 电源键和音量减通常来自 PMIC PON。
- 音量加通常来自 PMIC GPIO 与 gpio-keys。
- 引脚和去抖值使用本机原厂设备树及原厂值，而不是直接照搬参考设备。

### 键盘配件

键盘路线将协议实现与板级电气控制分开：
- 从厂商驱动抽取协议。
- 以 HID transport 或 serdev 方式实现。
- 协议核心独立并可测试。
- 板级部分补充电源、检测脚和方向脚。
- 与平板模式开关集成。

这并不是把所有键盘统一为同一种总线或协议；后续故障条目明确显示不同设备的 UART/I2C、主动心跳和事件驱动方式可能不同。

## 3. 完成标准

三类验收都落在真实输入与用户可观察行为上：

- **触控**：真实手指点击、滑动、多指、四角、横竖屏；冷启动、熄屏再亮屏、面板重新上电分别测试；多次冷启动后输入设备号稳定。中断计数、设备节点存在、程序注入事件都不算。
- **按键**：真实 evdev 按下/松开事件，以及桌面音量提示或符合设置的电源键行为。
- **键盘**：真实按键和组合键、拔下再吸附，以及熄屏后的恢复。

这里的验收边界不止于驱动层。它要求实际输入事件以及桌面行为能够被观察到。

## 4. 故障经验的不同机制

条目不是同一种“输入失效”问题，而是覆盖多个机制：

- TDDI 面板复位导致 RAM 中的触控固件丢失。
- 厂商命令帧被截短，驱动却用过弱条件报告升级成功。
- 分段固件漏写 CRC 覆盖范围之外的头部数据。
- THP 在数据帧到达前收到命令。
- GPI DMA 完成回调的状态设置时机影响 SPI 的 actual_length。
- 双 DSI 下触控 probe 早于面板就绪，且输入设备 parent 未设置。
- 坐标变换顺序与方向标定。
- 设备树缺少按键描述，或参考设备的引脚/去抖值不适用。
- 键盘配件已枚举，但总线仍因电源、电压或时钟问题不可用。
- 键盘协议帧、校验、UART 回波和主从发起顺序。
- GNOME 平板模式下的方向管理策略。
- 指纹状态映射、模板文件权限、PAM/session 验收和 secure-world 总线边界。
- 面板上电回调同步等待触控首帧，阻塞显示 kickoff。
- 磁吸键盘电源状态寄存器没有按原厂熄屏/亮屏生命周期写入。
- GNOME chassis 元数据对电源键设置界面及其他行为的影响。

这些条目字段并不统一。没有为源文件缺失的确认、原因或适用范围补造内容。

## 5. 显式跨文档关系

### 与 `display.md`

显示文档明确要求高刷新率与触控一起验收，并链接本文件。

触控文档进一步记录：面板 enable 回调中同步等待首帧会阻塞显示控制器 kickoff；不同刷新率下可能出现不同结果。这使显示生命周期/时序与触控行为之间的联系不仅是并列测试，还涉及回调顺序和首帧依赖。

但这不意味着所有触控问题都属于显示问题。TDDI 固件丢失、帧格式错误、DMA/SPI 行为和坐标标定各有独立机制。

### 与 `kernel-and-resources.md`

键盘配件条目明确引用该文件，说明缺少原厂常开电源可能导致总线保持低电平。它还列出 PMIC 电压步进和设备树时钟频率问题。

因此协议调试前需要先确认电气层和资源供给。HID 枚举成功不代表总线已经能正常传输键盘数据。

### 与 `patterns.md`

经验库索引要求新故障先对照通用问题模式。patterns.md 明确把触控/键盘案例列入：
- B：资源没有真正的拥有者（键盘总线电源）。
- C：时序和生命周期不对（TDDI 固件丢失、过早发命令、面板回调阻塞、键盘电源状态）。
- H：别人的实现不能整搬（键盘保活策略）。

这些模式归属来自源文件显式列举，不是本轮另行创建的触控分类。

## 6. 观察者重构出的对应关系

以下是跨文档观察者对应关系，不是源文件定义的新架构：

- **面板生命周期是共享依赖**：TDDI 的触控固件与显示状态通过面板复位和电源回调耦合。
- **回调顺序与非阻塞工作**：首帧案例把面板回调、显示 kickoff 和触控首个中断联系起来。它与面板复位导致固件丢失是不同机制，即使两者都可能在熄屏/亮屏后出现。
- **协议之前先确认电气就绪**：配件枚举成功不证明总线电气条件正常；电源、电压和时钟必须与协议问题区分。
- **用户边界的证据**：真实触控事件、桌面按键行为、键盘实际输入、指纹 PAM/session 解锁，比驱动日志或设备注册更接近验收目标。
- **设备特定来源**：同系列主线驱动或社区实现可提供结构参考，但板级数值、电气细节、标定和配件生命周期必须回到本机证据。
- **策略元数据有副作用**：修改 chassis 分类可能让 GNOME 显示电源键选项，但也改变睡眠行为和蓝牙对端看到的设备类别。

## 7. 保留的重要区分

- 独立触控、TDDI 和 THP 的固件与数据职责不同。
- RAM 固件因面板复位丢失，与命令过早发送、面板回调阻塞 kickoff 是不同问题。
- 固件升级成功日志、CRC 一致、中断计数或输入设备节点，均不能单独证明触控可用。
- 面板 probe 时机、输入设备 parent 设置、触控固件就绪是不同条件。
- 键盘总线电气问题必须与配件协议问题区分。
- HID 枚举不等于键盘输入可用。
- 磁吸键盘电源生命周期不能用其他设备的保活策略替代。
- GNOME 键盘吸附时不自动旋转被源文件描述为预期策略，而非缺陷。
- 指纹成败看 PAM/session 解锁状态，而不是驱动日志。
- RAM 启动时首次建立凭据仍会写安全存储，不是零写入。
- 手写笔虽然在标题中出现，但正文未提供专门处理方法。

## 8. 未解决与未明确之处

源文件明确保留三项未解决问题：

- THP 触控静止按住约一帧后被释放，运行时偶发整屏闪烁。
- 首次物理快捷键按下无响应。
- 平板吸附磁吸键盘开机时无法识别，拿下再吸附才识别。

此外，源文件没有建立：
- 手写笔专用路线、协议或验收标准。
- 触控/面板/键盘电源生命周期的统一状态模型。
- 覆盖所有输入设备的完整测试矩阵。
- 配件协议跨设备型号可移植性的通用判断标准。

这些缺失在当前重构中被保留，而不是用相邻文档的内容填补。
