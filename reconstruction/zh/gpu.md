## 1. 文档角色

该文档是 Adreno GPU 与图形栈的领域经验记录。它不是 GPU 驱动规范，也没有试图定义完整的图形架构。内容由推荐路线、完成标准、具体故障经验和未解决事项组成。

它涉及多个相互依赖但职责不同的层次：

1. 内核中的 drm/msm 支持，以及 GPU 时钟控制器、GMU、SMMU 和 OPP 表。
2. 固件：sqe、GMU、zap shader，以及零售设备安全世界对签名的限制。
3. 用户态 Mesa：完整 chip ID 识别、独立前缀安装和条件启用本地构建版本。
4. Snap 与 Flatpak 自带的 GL 库。
5. 新 GPU 的 Mesa 尚不成熟时，跟踪上游修复、按提交回移，并记录和最终偿还技术债。

因此，“驱动已加载”并不是该文档的完成定义。它要求从硬件识别、正确绘制、持续运行、电源转换，到桌面合成器和复杂应用的实际使用都得到覆盖。

## 2. 内部结构

### 推荐路线

五步路线从内核和固件进入 Mesa，再进入沙箱应用，最后处理新 GPU 的 Mesa 成熟度问题。

前四步描述不同层次的准备和使用；第五步是条件性路线：当新 GPU 的 Mesa 支持尚不成熟时，跟踪 stable/main 的修复，按提交回移，并把每次回移登记为技术债，待上游版本包含修复后替换。

源文件没有定义适用于所有平台组合的强制顺序，也没有把这些步骤形式化为状态机。

### 完成标准

四类结果共同构成验收：

- 渲染器确实是硬件 GPU，而不是 llvmpipe/softpipe。
- 输出逐像素符合预期。
- 多次电源转换后仍能绘制，长时间运行没有 GMU 错误或 hangcheck。
- 桌面合成器实际使用 GPU，帧率接近刷新率；浏览器、视频播放器、设置等复杂应用正确运行且不崩溃，GTK GL 与 Vulkan 路径均需测试。

这里存在重要的递进：硬件识别不等于画面正确，画面正确不等于持续稳定，单个测试程序成功也不等于桌面和复杂应用可用。

### 故障经验

条目覆盖多个不同故障表面：

- Mesa 设备表没有识别完整 chip ID，导致软件渲染回退。
- 显示资源被回收后，内存通路降速，表面上出现 GMU/GPU 超时。
- 多 GL 上下文创建时的共享列表竞态。
- Turnip 在 buffer 到 image 上传时使用错误的行距单位。
- 新 GPU 某些纹理格式路径尚不完整。
- 内核对 GMEM 基址的返回值错误。
- 新 GPU 上 Vulkan 挂起。
- QEMU 或软件渲染导致测试假通过。
- GDM 登录界面和压缩格式限制导致帧捕获失败。

条目字段并不完全一致。有的包含现象、原因、确认、解决和适用范围；有的只记录源文件实际提供的字段。重构没有为缺失字段补造内容。

## 3. 显式跨文档关系

### 与 kernel-and-resources.md

GPU 文档在资源回收条目中明确引用该文件。它指出：借用固件画面时，显示总线时钟可能被回收，导致内存通路降速，继而表现为 GMU HFI 超时或 hangcheck。

同一条目还列出另外两种 GPU 电源相关可能性：
- MX 依赖投票使用了错误的 OPP 表；
- 电源域被投到 retention 档。

诊断顺序是先排除显示侧资源问题，再检查 GPU 电源投票。

这是明确的跨文件引用和诊断顺序，但不是“所有 GMU 超时都由显示资源回收造成”的因果规则。

### 与 ubuntu-userspace.md

推荐路线明确指向该文件，说明 Snap 和 Flatpak 使用各自的 GL 库。这把沙箱应用的用户态库选择与主机 Mesa 路径区分开来。

### 与 touch-and-input.md

GPU 源文件没有直接引用触控文档。此前显示文档要求高刷新率与触控一起测试，并明确指向 touch-and-input.md。因此目前不能把这一要求改写成 GPU 文档本身的要求；是否形成更广泛的跨子系统验收关系，需要结合后续源文继续观察。

## 4. 观察者重构出的对应关系

以下是观察者对多个领域的对应理解，不是源文件定义的新分类：

- **资源连续性**：显示总线时钟的回收会影响 GPU 内存通路，即使可见症状由 GMU/GPU 监控报告。
- **分层职责**：内核支持、固件接受、Mesa 设备识别、沙箱库选择和应用绘制可以分别失败。
- **表示与实际状态**：测试可能在 Mesa 使用 softpipe/llvmpipe 时仍然通过；渲染器身份因此属于验收证据。
- **测量边界**：帧捕获工具可能不支持压缩格式，这不自动等同于显示或绘制失败；光标平面也不能代替主画面。
- **并发与生命周期**：共享 GL 上下文和电源转换可能暴露单上下文、短时渲染测试看不到的问题。
- **上游谱系与本地技术债**：按提交记录回移，使本地修复在上游版本包含相应修复后可以被替换。

这些对应关系有助于理解文档之间的联系，但不能回写为源文件已经定义的正式模式。

## 5. 保留的重要区分

- 硬件渲染器识别、输出正确和持续稳定是不同验收维度。
- 内核驱动支持、固件签名/可用性和 Mesa 识别是不同要求。
- 本地 Mesa 安装在独立前缀中，并按条件启用；它不是无条件替换发行版版本。
- Snap/Flatpak 的 GL 库与主机 Mesa 路径不同。
- GMU 超时可能涉及显示资源，也可能涉及 GPU 电源投票；仅凭症状不能确定原因。
- GL 与 Vulkan 是不同渲染路径，不能以一条路径的成功替代另一条。
- 软件渲染下测试通过，不构成硬件 GPU 加速证据。
- 帧捕获路径的限制，不自动意味着实际绘制失败。
- 源文件在提供时保留了变通方案的性能代价和回移的后续替换条件。

## 6. 未解决与未明确之处

- 新 GPU 的 Vulkan 稳定性、持续负载、调频和电源管理明确列在未解决事项中。
- 源文件没有提供适用于所有设备的固件选择与签名操作规程。
- 没有定义 GPU 电源转换的正式状态模型或完整测试矩阵。
- 没有给出 Mesa 成熟度的通用阈值；只说明上游发布包含修复后应替换本地回移。
- 多个故障条目没有提供确认步骤或完整适用范围；不能从其他条目推导并补齐。
