## 1. 文档角色

该文档是以高通 AudioReach/ADSP 为中心的音频 bring-up 经验记录。内容覆盖 DSP 前置条件、硬件拓扑、后端与功放复用、拓扑编译、PCM/DSP 播放图、功放启动与调参、麦克风路径、UCM/PipeWire、音量和用户侧验收。

它不是通用 Linux 音频参考。技术实例主要来自高通平台；Ubuntu、ALSA、UCM 和 PipeWire 的适用范围按原文保留。

## 2. 推荐路线的结构

源文件给出一个分层推进路线：

1. 先确保 ADSP 固件加载（PAS）、QRTR、PD mapper 和 GPR 正常。
2. 从原厂运行时设备树与 mixer 配置恢复真实硬件拓扑：扬声器后端是 TDM 还是 I2S、功放型号和数量、麦克风是数字直连 LPASS 还是模拟路径经过 codec/SoundWire。
3. 优先复用同 SoC 已经跑通的后端和功放驱动；固定 audioreach-topology 版本编译拓扑；必要时从原厂 ACDB 提取后端参数。
4. 按层推进：PCM open/configuration/prepare、DSP 接受播放图、功放启动、全零静音测试、电气回环、人耳确认。
5. 在全新系统验收 UCM/PipeWire；多声道扬声器需要上混配置。
6. 首次出声采用保守增益；正式产品增益是独立决定。

这里的“逐层推进”不意味着所有设备都有相同的物理后端或麦克风结构。拓扑首先由目标设备证据决定。

## 3. 完成标准：不同证据表面

源文件把验收拆成不同层次：

- **软件/DSP 与功放机器证据**：播放指针推进、错误计数为零、功放寄存器读回正常、调参文件版本正确、一次启动内没有功放或 DSP 错误。
- **机器可观测信号**：电气回环，或设备自身麦克风录到测试音。
- **人的听觉确认**：在约定时间窗口播放明显可听的测试音并由用户确认；多扬声器设备逐路确认。
- **麦克风功能**：外部声源出现/消失与录音相对应，并设置无声源对照。

所有验收都必须在没有保存 ALSA 状态的全新安装上完成。环境残留因此属于验收条件，而不是外围清理事项。

## 4. 故障条目覆盖的机制

条目分别涉及：

- TDM 位时钟极性和时钟属性。
- bootloader 改写根 compatible，而测试忽略异步错误。
- 远端处理器崩溃原因上报字段长度错误。
- 前端与后端 PCM 格式、声道数不兼容。
- DAPM 功放上电早于 TDM 位时钟出现，以及 PRM 时钟 ID。
- 上游拓扑片段端口号为 0，导致链路被丢弃。
- 设备树功放调参文件命名问题，以及修复未进入补丁序列后丢失。
- 安全 bring-up 增益进入正式版、驱动默认增益、缺少扬声器保护和 UCM 不暴露硬件增益。
- PipeWire 立体声上混。
- UCM 路由位置、缺失控件和保存的 ALSA 状态造成 Dummy Output。
- 外接显示输出打开失败导致 PipeWire 丢弃整个 profile，内置麦克风也随之消失。
- 主线 DSP 固定 DMA 通道假设，以及模拟/数字麦克风误判。
- 没有声源时错误地判定麦克风失败。
- Ubuntu ALSA sequencer 依赖。
- 自写测试工具掩盖 PipeWire MMAP 预填死锁。
- 将厂商功放遥测误当作实际输出证据。
- 功放驱动要求不存在的电源，以零电压占位 regulator 临时满足 binding。
- 厂商增益与缺少 ADSP 扬声器保护之间的安全取舍。

这些条目不是统一模板：有些没有单独的确认或预防字段。当前重构没有补造缺失字段。

## 5. 显式跨文件关系与集合层关系

音频源文件本身没有 Markdown 跨文件链接。以下联系来自经验索引和相邻源文，不应误称为 audio.md 内的直接引用。

### patterns.md：残留状态（模式 D）

Pattern D 明确把 audio.md 列为全新安装只有 Dummy Output 的案例。其通用处理是列出残留状态，在全新系统/新启动/空目录复现，并在无残留条件下验收。

audio.md 的 UCM/PipeWire 验收要求没有 `/var/lib/alsa/asound.state`，与该模式直接对应。模式索引关系是明确的；具体音频根因仍由 audio.md 记录。

### patterns.md：底层通过不等于用户能用（模式 F）

Pattern F 要求从硬件到用户入口追踪完整链路，并且只有在最终用户入口通过后才关闭用户报告的问题。

audio.md 从 DSP 和功放状态推进到回环、录音和人耳确认，是该证据边界在音频领域的具体表现。这是跨文件观察者对应关系，不是 audio.md 自己定义的音频分类。

### kernel-and-resources.md

内核/资源文档把 `SND_SEQUENCER` 列为缺失时可能静默影响桌面功能的内核配置，并指出 Ubuntu ALSA hook 要求 `snd-seq`。audio.md 记录对应用户侧现象：USB 声卡或 codec 驱动不能自动加载，需启用并打包 `SND_SEQUENCER=m`。

这是两个文档共同呈现的技术依赖，但不能据此推断所有音频 bring-up 故障都是内核模块问题。

### experience/README.md

经验库索引规定先看 patterns，再到领域文件；只有根因已确认的问题进入“坑”，未解决事项放在文末。audio.md 遵循这一集合维护方式。这是集合层关系，不是 audio.md 内的直接链接。

## 6. 观察者重构出的对应关系

以下是跨源材料观察所得，不是源文件定义的新架构：

- **分层证据**：PCM 配置成功、DSP 接受播放图、功放启动、电气输出和人耳可闻是不同观察。某一层通过不能证明下一层通过。
- **拓扑由设备证据确定**：同 SoC 复用提供基线；目标设备原厂运行时设备树、mixer 配置和 ACDB 数据确定实际拓扑及后端参数。
- **异步错误通道不可忽略**：同步 `prepare` 返回成功时，日志仍可能随后出现功放/APM/ADSP 错误。
- **测量需要刺激和对照**：麦克风验收需要外部声源和无声源对照；功放遥测不是输出证据。
- **全新状态与可复现性**：保存的 ALSA 状态可能掩盖 UCM 路由或控件错误。全新安装会改变系统首次运行时实际暴露的行为。
- **安全与产品策略**：首次出声的保守增益、产品增益和原厂扬声器保护是不同决定。没有等效保护却提高增益，是用户可见的硬件风险，不只是调音问题。
- **生命周期与服务状态**：WirePlumber 崩溃后 APM/PRM 请求不再响应，但源文件没有说明恢复机制，除重启外没有给出解决路线。

## 7. 保留的重要区分

- ADSP/PAS、QRTR、PD mapper 和 GPR 就绪是前置条件，不是音频输出证据。
- 后端类型、功放型号/数量和麦克风路径属于硬件拓扑问题。
- 前端 PCM 能力与 DSP/后端能力可能不一致。
- 功放启动可能必须等到 TDM 位时钟出现。
- 播放图打开和 `prepare` 成功不等于人耳可闻。
- 调参文件身份/版本与功放驱动注册是不同问题。
- 安全 bring-up 增益不必然适合作为产品增益。
- PipeWire profile 可用性可能把输出与麦克风暴露耦合起来。
- 保存的 ALSA 状态可能让开发机通过、全新安装失败。
- 没有声源的麦克风测试不能作为有效失败结论。
- 厂商功率/电压遥测不能替代回环、录音或听觉确认。
- 零电压占位 regulator 是临时 workaround 和技术债，不是已确认的真实供电。
- 缺少 ADSP 扬声器保护会限制安全最大增益。

## 8. 未解决与未明确之处

源文件明确保留三项未解决问题：

- 主线没有 ADSP 扬声器保护模块，因此最大音量受限。
- 启动时偶发的功放上电错误是否无害，尚不确定。
- WirePlumber 崩溃后，ADSP APM/PRM 请求不再响应，只有重启恢复。

源文件没有建立：
- 适用于所有高通音频设备的统一拓扑。
- 所有麦克风、功放和后端变体的完整映射。
- WirePlumber/APM/PRM 故障的一般恢复程序。
- 不依赖具体功放和保护实现的量化安全增益上限。

这些缺失不从外部音频资料中补齐。
