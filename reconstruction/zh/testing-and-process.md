## 3. 主要可见区分

### 3.1 执行成功与功能可用

源文反复区分：
- 进程、服务、probe 或模拟环境能够运行；
- 底层接口或硬件指标达到某种状态；
- 用户能够通过实际入口看到、听到、触摸到或连接到功能；
- 人对实际结果的确认。

这些证据不能相互替代。影子缓冲有图、`hci0` 已启动、服务 active、QEMU 通过，均不足以单独证明用户功能可用。用户报告的问题应从用户实际使用的入口验收后才关闭。

### 3.2 离线证据与真机证据

离线检查、重复构建比较和 QEMU 测试可以形成证据，但不能自动构成接近交付的证明。源文要求：
- 仅有离线证据时明确标为“离线通过”；
- 新功能先在独立 RAM 镜像上逐项进行真机验证，再合并；
- 保存真机原始数据；
- 改动启动路径的组件后，使用包含该改动的镜像进行冷启动验证。

这不是对离线测试价值的否定，而是对其证据范围的限制。

### 3.3 测试对象也可能出错

错误可能来自测试对象，也可能来自：
- 验收判据；
- 编排器和包装器；
- 测试数据；
- 主机侧脚本；
- 输出截取和哈希过程；
- 时钟、场景或环境等测量条件；
- 测试开始时机。

源文提出为每项检查准备一个预期失败的输入，并在工具修复后重新判断已保存证据，而不是重跑设备或放宽标准。

### 3.4 归因与排除

源文不接受单个数据点直接支撑根因结论。它要求用第二个数据点或对照组尝试推翻解释，并先确认测量方式可信。

同样，排除实验应从干净的新启动开始。若其他条件尚未得到确认，就不应把“没有看到改善”升级为“改动无效”。

### 3.5 主机、设备与用户之间的边界

主机脚本并非透明、可靠的外围工具；其地址、路由、终端、换行、退出码、输出边界、USB 重新枚举和 Fastboot 交接均可能污染真机测试。

用户动作则有自己的时间边界：需要用户操作时要提前通知，说明动作和观察目标；可由长时间记录器捕获的，不必依赖短暂窗口。自动化可以减少用户操作，但注入事件只能证明软件路径，不能替代至少一次真实手指确认。

设备实验还有操作者边界：同一时刻只允许一个操作者；每份证据绑定 boot ID；没有 boot ID 的主机日志不能用于归因。

### 3.6 协作与连续性

NO-GO 记录用于保存被否定的方案和撤销的改动，避免上下文压缩或换人后重新引入同一错误。

子 agent 的任务说明被要求限制为：
- 一种做法；
- 允许修改的文件；
- 一条验证命令；
- 通过标准；
- 停止条件。

任务开始后要尽早检查方向。除非测试方式与真实使用方式一致，否则子 agent 声称“已测试”仍按未验证处理。

候选内核事故进一步显示：经验库中存在安全规则，不等于执行者实际收到这些规则。规则必须进入具体任务说明；硬件第一次故障出现后应停止测试、取证、恢复并汇报，而不是在同一次启动里继续操作。

### 3.7 复用、外部表达与贡献边界

设计流程前先查看同 SoC、同作者项目的安装器、复盘和技术债。复用社区成果前先比较设备树路线、资源管理、init 和安装方式，再决定整体更换基线或按功能系列导入。

外部文档面向首次接触项目的人；一个结论只由一个位置持有；发布前由主 agent 审查。社区贡献尽可能合并，但与项目范围无关或有法律、道德风险的内容不收，合入后记录作者和来源。

## 5. 观察者重构出的对应关系

以下是跨条目观察到的对应关系，不是源文定义的正式模型：

- **证据层次**：服务/probe/模拟器状态、硬件指标、用户可感知输出和人工确认是不同证据面。
- **测试系统本身也是观察对象**：判据、编排器、包装器、测试数据、主机脚本和观测方法均可能制造错误结果。
- **可证伪性**：负向输入、对照组和第二个数据点用于挑战表面通过状态或根因解释。
- **干净状态依赖**：boot ID、干净启动、RAM 镜像、用户/会话状态、旧包和槽位内容影响结果能否归因。
- **操作者与任务串行化**：单设备单操作者、证据绑定启动身份和受限任务说明减少相互干扰。
- **知识存储与知识送达的差异**：候选内核事故区分了规则存在于经验库，与规则进入当前执行者任务说明这两件事。
- **恢复能力与实验许可**：实验行为受设备可恢复性约束；无人值守驱动操作和候选写槽具有明确恢复风险。
- **用户验收与自动化的边界**：自动化减少不必要的用户动作，但不能抹去软件注入事件与真实物理交互之间的区别。
