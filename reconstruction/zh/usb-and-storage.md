该文件覆盖 USB 设备/主机角色、Type-C 与 UCSI、外接显示、UFS、分区、双系统、刷写、根文件系统交付和安装工具。它沿用经验库结构：推荐路线、完成标准和坑。

推荐路线包含五个操作分组：

1. 先建立 USB 设备模式作为调试通道，再推进主机模式和外接显示。
2. 存储控制器与 PHY 内建，通过 PARTLABEL/GUID 定位分区。
3. 以活动槽镜像集轮换实现双系统，而不是把两个 Android A/B 槽简单视为 Linux/Android 两个独立系统槽。
4. 在设备上格式化并解压 tar 交付根文件系统，保留扩展属性和数字属主。
5. 使用只在内存中运行、不挂载分区、超时返回 Fastboot 的维护镜像。

完成标准直接覆盖设备和用户可见行为：外设读写与拔插恢复、USB 3 速率证据、外接显示和断开恢复、调试通道恢复、分区写后读回、真机双系统循环及冷启动，以及包括 GNOME 首次设置在内的完整安装。

## 3. 推荐路线与证据边界

### USB 与外接显示

源文件明确给出顺序：先做设备模式，作为调试通道，优先 USB 2 高速 NCM；然后做主机模式和外接显示。启用顺序为：

控制器角色切换 → UCSI → VBUS → 枚举 → USB 3 / DP。

验收不止是枚举成功，还包括 U 盘读写、鼠标、拔插恢复、USB 3 速率证据、外接显示器画面及 EDID/模式信息、拔出后的恢复，以及切换后的调试通道恢复。

故障条目区分：
- USB 网络接口命名冲突；
- NCM 大文件传输停滞；
- UCSI 复位重试风暴导致 ADSP 无响应；
- 主机模式 PHY 参数表、属性、用户态控制和时钟顺序问题；
- 单 Type-C 口切换角色导致调试通道丢失；
- 外接显示切换芯片身份、位图/引脚表示、HPD 误报、SBU 驱动内建要求和内屏原生接管前提；
- UCSI 逻辑供电状态与物理供电之间的区别。

### 存储、分区与备份

源文件偏好存储控制器/PHY 内建，并使用 PARTLABEL/GUID 稳定定位分区，而不是依赖会变化的设备名。它指出 `sdX` 名称会随启动变化，主线控制器名也可能与 Android 不同。

备份记录明确区分“逐分区状态”和原子快照。GPT 表区填充、FAT 分区无法冻结、root 权限不足、活跃分区读取等因素都会影响备份完整性或一致性。所述流程要求在主机和设备两侧计算哈希。

此外，源文件指出，即使只是只读识别磁盘，UFS 驱动加载时仍可能写入某些设备属性。这里记录的是需要考虑的行为，不是说整个操作都只读。

### 双系统、槽位与刷写

源文件采用活动槽镜像集轮换模型：

- 两个系统都从当前活动槽启动；
- 切换时把目标系统启动镜像集写入活动槽；
- 另一套系统保留在 Linux 分区；
- 系统内切换用 `dd`，Android 侧用 KernelSU 模块；
- 启动后由服务标记槽成功。

多个故障条目说明，槽状态不能简化为一个属性位：
- bootloader 校验还涉及各 LUN 上成对分区类型 GUID 的互换及启动 LUN；
- 主机端 `fastboot flash` 会重置重试计数；
- Android 依赖启动链以外的固件分区；
- 如果轮换工具没有先识别当前活动槽实际内容，写入失败时可能删除正在使用的镜像集。

稀疏镜像的两种块语义必须分开：
- FILL 写零。即使 Fastboot 已返回 OKAY，后台写入仍可能持续很久。
- DONT_CARE 跳过写入，因此设备旧数据会保留；固定文件系统 UUID 还可能使旧日志在崩溃恢复时被重放。

这不是笼统的“稀疏镜像损坏”问题，而是两种不同的写入后果。

恢复建议强调谨慎：先获取 bootloader 失败证据，再改变槽状态；机制不清楚时避免状态变更型诊断；写入后读回；不一致时恢复原镜像且不重启。

### 安装与维护镜像

推荐的根文件系统交付方式是在设备上格式化，再用 tar 解压，保留扩展属性和数字属主。若必须交付镜像，则只编码已使用块。

维护镜像是内存中的安装/恢复环境，包含存储驱动、root shell 和分区工具；不挂载分区，并在超时后返回 Fastboot。它也被用于写分区表和首启前预置本机文件。

安装验收要求依照公开文档，在真机上从干净状态完成整个流程，包括 GNOME 首次设置。相关故障包括：
- 主机端接受“保留 home”参数，但设备端未收到，仍无条件格式化；
- 内存安装环境缺少工具或工具语义不同；
- BusyBox tar 不保留扩展属性；
- USB 网络未就绪或主机端口冲突导致 HTTP 服务无法启动；
- 首启时缺少本机校准、地址等数据；
- 必须记录首启前后状态差异。

## 5. 观察者重构出的对应关系

以下是观察者从文档内部及跨文档比较中重构出的对应，不是源文件定义的正式统一模型：

- **调试通道作为操作依赖：**先建立 USB 设备模式作为调试通道。单 Type-C 口切换到主机模式可能切断通道，因此源文件进一步要求在物理操作前建立第二条 Wi-Fi SSH 通道并设置定时回退。
- **逻辑状态与物理状态：**Fastboot OKAY 不证明后台写入完成；UCSI 供电状态不证明物理供电；bootloader 槽属性不完整代表槽有效性；主机端接受“保留 home”参数不证明设备端脚本实际收到。
- **身份与枚举名称：**分区和设备身份应通过控制器、LUN、GPT GUID、label 和几何信息重新确认，不能依赖临时 `sdX` 名称。
- **写入语义与残留数据：**FILL 和 DONT_CARE 的操作后果相反：前者写零并可能非常慢，后者跳过写入并可能保留旧数据。文件系统元数据和日志区还有各自的写入要求。
- **类似事务的安全边界：**槽轮换要求先识别当前内容，再写入、读回、校验；不一致时恢复，且不重启。安装则要求验证设备端实际效果，而非相信主机端参数。这与分阶段事务有对应，但源文件没有定义正式事务协议。
- **恢复能力的保留：**维护镜像、定时回退、第二条 SSH 通道、写入不一致时禁止重启，以及避免无人值守卸载驱动，都在保护失败后的恢复能力。
- **本机数据与可分发数据：**校准、地址等唯一数据不能进入公开镜像，必须由安装流程在首启前单独预置。
- **端到端证据：**验收超越命令返回或节点出现，延伸到读回、外设行为、断开恢复、真实启动循环和干净安装。

这些对应关系可用于比较，但不能据此声称源文件已定义统一事务、恢复或状态机架构。
